## الطبقات الخمس

كل طبقة تتحدث مع التي تحتها فقط — لا وصول مباشر من الواجهة لقاعدة البيانات.

```
① العرض        customer-pwa · merchant-dashboard · admin-panel · شاشة الكاشير
                            ▼  HTTPS / JSON
② الحافة        nginx / Traefik — TLS · gzip · rate limit · رؤوس الأمان
                            ▼  ASGI
③ التطبيق       Django 5 + DRF — مصادقة · صلاحيات · محرك القيود · محرك القواعد
                            ▼
④ المهام        Celery worker + beat — تدوير الرموز · الرسائل · الانتهاء · التقارير
                            ▼
⑤ التخزين       PostgreSQL (الحقيقة) · Redis (رموز · كاش · طوابير) · S3 (ملفات)
```

## القواعد المعمارية غير القابلة للكسر

كسر أي منها يعني إعادة بناء، لا إصلاحًا:

1. **كل تعديل على الرصيد يمر عبر `apps.ledger.services.apply_entry()`.**
   لا يوجد في المشروع كله سطر آخر يكتب في جدول `Balance`.
2. **`LedgerEntry` بنمط append-only** — لا `UPDATE` ولا `DELETE`. التصحيح بقيد عكسي عبر `reverses_id`.
3. **`select_for_update()` على صف الرصيد** — بدونه ضغطتان متزامنتان تمنحان النقاط مرتين.
4. **التسلسل الهرمي كامل من اليوم صفر** — مؤسسة ← علامة ← فرع ← نقطة بيع ← كاشير، حتى لو لم يُستخدم كله.
5. **رصيد منفصل لكل علامة** — عبر `Membership`. المنصة ليست نظام مقاصة مالية بين التجّار.
6. **منطق الأعمال في `services.py` فقط** — الـ View يستقبل ويتحقق ويستدعي. نفس المنطق يُستدعى من API ومن Celery ومن أوامر الإدارة بلا تكرار.
7. **مفاتيح ميزات حسب الباقة** — الباقات الثلاث من قاعدة كود واحدة. الترقية = متغيّر بيئة ونشر.

## تدفق العملية الحرجة

دورة «رمز ← مسح ← تأكيد ← نقطة» — الطريق الذي يمر به كل جنيه في النظام.

| # | الخطوة | التفاصيل |
|---|---|---|
| ١ | تدوير رمز نقطة البيع | مهمة Beat كل ٣٠ ثانية تولّد رمزًا لكل `Terminal` نشط في Redis بمفتاح `pos:code:{code} → terminal_id` و `TTL=35s` |
| ٢ | العميل يمسح | `POST /scan/resolve {code}` — غير موجود أو منتهٍ ← `410 Gone`. ناجح ← بيانات العلامة والفرع والبرامج ومعاينة الرصيد |
| ٣ | إدخال قيمة الفاتورة | `POST /transactions` ← سجل بحالة `pending`. **لا تُمنح أي نقطة هنا.** الرمز يُستهلك من Redis فورًا |
| ٤ | التاجر يؤكّد — **ذرّي** | `POST /pos/transactions/{id}/confirm` في معاملة واحدة: قفل العضوية ← تطبيق القاعدة ← فحص السقوف ← كتابة القيد ← تحديث الرصيد ← سجل التدقيق ← قواعد الاحتيال |
| ٥ | ما بعد التأكيد — غير متزامن | `on_commit` فقط: Web Push · Webhook · تحديث المؤشرات · إعادة حساب الالتزام القائم. فشل أي منها لا يؤثر على صحة الرصيد |
| ٦ | الاستبدال | `POST /redemptions` — نفس النمط الذري بـ `delta` سالب و `reason=redeem`، ثم كود صالح ١٥ دقيقة |
| ٧ | انتهاء الصلاحية | مهمة يومية تكتب قيدًا بـ `reason=expire`، وتنبيه مجاني قبل الانتهاء بثلاثين يومًا |
